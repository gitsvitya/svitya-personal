# Сборка и публикация svitya.com на тарифе Восток-1

Пошаговый порядок для вашего обычного виртуального хостинга Спринтхост на тарифе
«Восток-1». В панели доступен Node.js 22, а в SSH подтверждена версия `v22.9.0`.
Сборку для Linux готовим на Mac через Docker, затем загружаем готовый комплект.
Команды разделены на те, которые выполняются на Mac, и те, которые выполняются
на сервере после подключения по SSH.

Сайт работает как приложение Next.js. Для публикации нужен комплект `.next/standalone`
и серверный запуск через Passenger, который управляет приложениями на обычном хостинге
Спринтхост. Большинство страниц создается при сборке, но выбор языка, перенаправления
и обработка изображений используют сервер.

## 0 Параметры вашей публикации

| Параметр            | Значение                               |
| ------------------- | -------------------------------------- |
| Тариф               | «Восток-1»                             |
| Тип услуги          | Обычный виртуальный хостинг Спринтхост |
| Версия в панели     | Node.js 22 доступен                    |
| Версия в SSH        | `v22.9.0`                              |
| Среда сборки        | Linux через Docker на Mac              |
| Управление запуском | Passenger                              |
| Основной домен      | `svitya.com`                           |

«Восток-1» входит в линейку архивных тарифов виртуального хостинга; это подтверждает
[официальная информация Спринтхост](https://sprinthost.ru/news/20220831).
Сайт будем запускать через Passenger по описанному ниже порядку.

Подготовьте данные SSH в шаге 1 и проверьте сайт на Mac в шаге 2. В шаге 3 уточните
архитектуру сервера и путь к `node22`. Далее выполняйте шаги по порядку.

**Сборка и запуск требуют разных версий Node.js.** Сборка включает проверку содержимого
через Vitest; установленные в проекте Vitest и Vite требуют Node.js 22.12.0 или новее
в ветке 22. Поэтому на сервере с `22.9.0` не выполняем `npm ci` и `npm run build`.
Для готового комплекта Next.js и sharp заявляют минимум Node.js 20.9.0;
см. [требования Next.js](https://nextjs.org/docs/app/getting-started/installation)
и [требования sharp](https://sharp.pixelplumbing.com/install/).

7 октября 2026 года готовый сайт проверен локально на Mac с Node.js **22.9.0**:
работают русские и английские страницы, PDF, sitemap, robots, перенаправление языка
и обработка изображений. Это не подтверждает запуск через Passenger на вашем аккаунте:
его проверяем после публикации в шаге 10. Желательно также попросить поддержку обновить
Node.js до актуального выпуска ветки 22; для описанного пути сборки это не обязательное условие.

## 1 Что подготовить

В панели Спринтхост найдите:

- логин аккаунта;
- IP-адрес сервера в разделе «Сайты» → «IP-адреса»;
- пароль или настроенный SSH-ключ;
- сайт `svitya.com` и его каталог `public_html`.

Проверьте доступ по SSH. Если он выключен или ограничен в настройках аккаунта, разрешите
его для своего подключения. Данные подключения описаны в
[инструкции Спринтхост по SSH и SFTP](https://help.sprinthost.ru/file-transfer/ssh-and-sftp).

Для локальной проверки на Mac используйте Node.js 24, как в проверках проекта.
Для Linux-сборки понадобится запущенный Docker Desktop. Если он еще не установлен,
используйте [официальную инструкцию для Mac](https://docs.docker.com/desktop/setup/install/mac-install/).
Docker нужен только на Mac: устанавливать его на Спринтхост не требуется.
Доступность Node.js 22 и порядок его выбора на хостинге описаны в
[инструкции Спринтхост по Node.js](https://help.sprinthost.ru/howto/nodejs).

Сначала подготовьте новую сборку и резервную копию. Переключать веб-сервер действующего
сайта будем в шаге 8.

## 2 Проверка и сборка на Mac

Откройте «Терминал» на Mac и перейдите в проект:

```bash
cd /Users/victor/Documents/git/svitya-personal
git status --short
node --version
npm --version
```

`git status` показывает локальные изменения. В дальнейшем архивируется текущее содержимое
папки, включая незафиксированные изменения. Убедитесь, что это именно та версия сайта,
которую нужно опубликовать. Специально переключать ветку или удалять изменения не требуется.

Выполняйте следующие команды по очереди. При ошибке остановитесь и исправьте ее, прежде
чем переходить к следующей команде:

```bash
npm ci
npm run check
npm run build
```

`npm ci` устанавливает версии из `package-lock.json`. `npm run check` проверяет содержимое,
код, типы, тесты и форматирование. `npm run build` создает готовый комплект приложения.
Браузеры Playwright для этих трех команд устанавливать не нужно.

В конце успешной сборки должна появиться строка:

```text
Standalone build includes public materials and static assets.
```

Готовый каталог имеет такую структуру:

```text
.next/standalone/
  server.js
  package.json
  node_modules/
  .next/
    server/
    static/
    ...
  public/
```

Скрипт `scripts/prepare-standalone.mjs` уже копирует `public` и `.next/static` в этот
каталог. Дополнительное ручное копирование для локального запуска не требуется.
Назначение комплекта описано в
[документации Next.js о standalone](https://nextjs.org/docs/app/api-reference/config/next-config-js/output).

Запустите собранный сайт на Mac:

```bash
PORT=3101 HOSTNAME=127.0.0.1 npm start
```

Откройте [русскую версию](http://127.0.0.1:3101/ru/about) и
[английскую версию](http://127.0.0.1:3101/en/about). Проверьте изображения, переходы,
галереи и открытие документов. Если порт занят, замените `3101` на свободный номер
и используйте его в адресе браузера. Остановите локальный сервер сочетанием `Control+C`.

### Почему эту сборку с Mac нельзя просто перенести на хостинг

В комплект входят платформенные зависимости, в частности `sharp` для обработки
изображений. На Mac устанавливается версия для macOS, а серверу нужна версия для Linux
и его архитектуры. Это ограничение описано в
[документации sharp](https://sharp.pixelplumbing.com/install/).

Поэтому основной путь ниже: проверить сайт на Mac, отдельно собрать Linux-комплект
через Docker и отправить его на хостинг. Сборка непосредственно на сервере описана
в разделе 12, но доступна только после обновления `node22` до 22.12.0 или новее.

## 3 Подключение к хостингу

В терминале на Mac задайте свои данные вместо `LOGIN` и `SERVER_IP`:

```bash
SVITYA_LOGIN='LOGIN'
SVITYA_SERVER='SERVER_IP'
SVITYA_RELEASE='20261007-01'
ssh "$SVITYA_LOGIN@$SVITYA_SERVER"
```

`20261007-01` здесь означает первую публикацию 7 октября 2026 года. При каждом обновлении
выбирайте новое имя, например `20261007-02`. Используйте одно и то же имя на Mac и сервере.

При первом подключении сверьте адрес сервера и подтвердите его ключ. Если появляется
запрос пароля, введите его: символы при вводе не отображаются.

После подключения следующие команды выполняются **на сервере**:

```bash
pwd
node22 --version
command -v node22
uname -m
getconf GNU_LIBC_VERSION
df -h .
```

Сохраните полный путь из `command -v node22`: он понадобится для `.htaccess`.
На вашем сервере `node22` вернул `v22.9.0`; в основном варианте его используем только
для запуска. На диске должно хватать места для архива, новой сборки и резервной копии.

Сохраните также архитектуру из `uname -m` для шага 6. Для выбранного Linux-комплекта
sharp нужна glibc не ниже 2.28. Если `getconf GNU_LIBC_VERSION` сообщает более старую
версию или команда недоступна, сначала уточните совместимость у поддержки.

На хостинге команды `node` и `npm` без номера могут запускать старую версию. Для работы
с этим сайтом будем явно использовать Node.js 22.

## 4 Резервная копия текущего сайта

На сервере задайте имя публикации и каталог сайта. Если панель показывает другой путь
к `public_html`, используйте его вместо указанного ниже:

```bash
SVITYA_RELEASE='20261007-01'
SVITYA_WEBROOT="$HOME/domains/svitya.com/public_html"
mkdir -p "$HOME/backups"
tar -czf "$HOME/backups/svitya-public-html-$SVITYA_RELEASE.tar.gz" \
  -C "$SVITYA_WEBROOT" .
ls -lh "$HOME/backups/svitya-public-html-$SVITYA_RELEASE.tar.gz"
```

Архив сохраняется вне публичного каталога и включает скрытые файлы, в том числе
существующий `.htaccess`. Также запишите текущий тип веб-сервера в панели.

Если сайт уже работает по этой инструкции, его серверная часть находится отдельно,
в `~/apps/svitya/releases/`. Сохраняйте и предыдущий каталог приложения: архив
`public_html` не включает его.

## 5 Подготовка исходников на Mac

Откройте вторую вкладку терминала **на Mac**. Первая вкладка может оставаться подключенной
к серверу. В новой вкладке переменные нужно задать заново:

```bash
cd /Users/victor/Documents/git/svitya-personal
SVITYA_RELEASE='20261007-01'

COPYFILE_DISABLE=1 tar \
  --exclude='.git' \
  --exclude='node_modules' \
  --exclude='.next' \
  --exclude='.env*' \
  --exclude='.DS_Store' \
  --exclude='.codex' \
  --exclude='.agents' \
  --exclude='.claude' \
  --exclude='.cursor' \
  --exclude='deploy' \
  --exclude='build' \
  --exclude='out' \
  --exclude='output' \
  --exclude='docs/editorial' \
  --exclude='test-results' \
  --exclude='playwright-report' \
  --exclude='coverage' \
  --exclude='*.log' \
  --exclude='*.jsonl' \
  --exclude='*.tsbuildinfo' \
  -czf "/tmp/svitya-source-$SVITYA_RELEASE.tar.gz" .

ls -lh "/tmp/svitya-source-$SVITYA_RELEASE.tar.gz"
```

Архив пока остается на Mac. Он включает `package.json`, `package-lock.json`, `app`,
`src`, `public`, настройки и скрипт подготовки сборки.
В него не входят установленные зависимости, локальная сборка, файлы `.env`
и служебные материалы.

В текущем коде сайта пользовательские переменные окружения не используются. Если позднее
они появятся, потребуется отдельно настроить их для сборки или серверного запуска.

## 6 Linux-сборка на Mac и отправка готового сайта

Команды сборки выполняются **на Mac**, не в SSH-сессии. Откройте Docker Desktop
из папки «Программы» или командой:

```bash
open -a Docker
```

Дождитесь готовности Docker. Затем проверьте, что команда видит запущенный сервер Docker:

```bash
docker version --format '{{.Server.Version}}'
```

Выберите архитектуру по результату `uname -m` на сервере:

- `x86_64` соответствует `linux/amd64`;
- `aarch64` соответствует `linux/arm64`.

Блок ниже рассчитан на `x86_64`. Для `aarch64` замените `linux/amd64` на `linux/arm64`.
Если результат другой, не угадывайте архитектуру: уточните подходящую среду сборки.
Используйте новое имя публикации и пустой каталог сборки для каждой версии.

```bash
cd /Users/victor/Documents/git/svitya-personal
SVITYA_RELEASE='20261007-01'
SVITYA_PLATFORM='linux/amd64'
mkdir -p "deploy/linux-build-$SVITYA_RELEASE"
tar -xzf "/tmp/svitya-source-$SVITYA_RELEASE.tar.gz" \
  -C "deploy/linux-build-$SVITYA_RELEASE"

docker run --rm --platform "$SVITYA_PLATFORM" \
  --mount "type=bind,source=$PWD/deploy/linux-build-$SVITYA_RELEASE,target=/app" \
  --workdir /app \
  node:22-bookworm \
  sh -ec 'node --version && npm ci --include=dev && npm run build'
```

Версия Node.js в контейнере должна быть не ниже 22.12.0. Она не зависит от версии
на Спринтхосте. `--include=dev` нужен, поскольку сборка использует TypeScript и Vitest.
При первом запуске Docker скачает образ; сборка другой архитектуры может занять больше времени.

Зависимости устанавливаются в отдельной папке `deploy`, поэтому рабочий `node_modules`
на Mac остается пригодным для macOS. `node:22-bookworm` использует Linux с glibc;
варианты образов описаны в
[официальном репозитории Node.js Docker](https://github.com/nodejs/docker-node/blob/main/README.md).

Дождитесь успешного завершения сборки и сообщения
`Standalone build includes public materials and static assets.`
Затем упакуйте **содержимое** готового каталога, включая скрытую `.next`, и отправьте архив:

```bash
COPYFILE_DISABLE=1 tar -czf "/tmp/svitya-linux-$SVITYA_RELEASE.tar.gz" \
  -C "deploy/linux-build-$SVITYA_RELEASE/.next/standalone" .
SVITYA_LOGIN='LOGIN'
SVITYA_SERVER='SERVER_IP'
scp "/tmp/svitya-linux-$SVITYA_RELEASE.tar.gz" \
  "$SVITYA_LOGIN@$SVITYA_SERVER:~/"
```

Теперь вернитесь во вкладку с **SSH-подключением** и распакуйте готовый сайт
в новый пустой каталог версии:

```bash
SVITYA_RELEASE='20261007-01'
SVITYA_RELEASE_DIR="$HOME/apps/svitya/releases/$SVITYA_RELEASE"
mkdir -p "$SVITYA_RELEASE_DIR"
tar -xzf "$HOME/svitya-linux-$SVITYA_RELEASE.tar.gz" -C "$SVITYA_RELEASE_DIR"
mkdir -p "$SVITYA_RELEASE_DIR/tmp"
cd "$SVITYA_RELEASE_DIR"
ls -la
node22 --check server.js
node22 -e 'console.log(require("sharp").versions)'
```

Проверьте наличие `server.js`, `node_modules`, `.next/static` и `public`.
Последняя команда должна вывести версии библиотек обработки изображений без ошибки.
На хостинге для этого комплекта **не выполняйте `npm ci` или `npm run build`**:
все необходимые зависимости и результаты сборки уже включены.
Если каталог с этим именем уже создавался при неудачной попытке, выберите новое имя
и последовательно используйте его в архиве, пути приложения и `.htaccess`.

## 7 Публичные файлы и настройка Passenger

Серверные файлы приложения остаются в `~/apps/svitya/releases/`. В публичный каталог
копируются материалы, изображения, шрифты и браузерные файлы сборки.
Спринтхост использует связку nginx и Apache; nginx отдельно обслуживает статические файлы.
Поэтому эти файлы должны быть доступны в каталоге сайта. См.
[описание веб-серверов Спринтхост](https://help.sprinthost.ru/how-hosting-work/webservers).

На сервере выполните:

```bash
SVITYA_WEBROOT="$HOME/domains/svitya.com/public_html"
cp -a "$SVITYA_RELEASE_DIR/public/." "$SVITYA_WEBROOT/"
mkdir -p "$SVITYA_WEBROOT/_next/static"
cp -a "$SVITYA_RELEASE_DIR/.next/static/." "$SVITYA_WEBROOT/_next/static/"
printf '%s\n' "$SVITYA_RELEASE_DIR"
command -v node22
```

Сохраните два последних значения: полный путь к приложению и путь к Node.js 22.

Через файловый менеджер панели или SFTP откройте файл
`domains/svitya.com/public_html/.htaccess`. Если его нет, создайте обычный текстовый файл
с этим именем. Замените правила старого сайта следующим содержимым, предварительно
убедившись, что резервная копия из шага 4 создана:

```apache
PassengerEnabled on
PassengerAppType node
PassengerAppRoot /home/LOGIN/apps/svitya/releases/20261007-01
PassengerStartupFile server.js
PassengerNodejs /usr/local/bin/node22
PassengerAppEnv production
PassengerResolveSymlinksInDocumentRoot on
Require all granted
Options -Indexes -MultiViews
```

Замените `PassengerAppRoot` на **полный путь**, выведенный командой выше.
Замените путь после `PassengerNodejs` на результат `command -v node22`.
Пути `/home/LOGIN/...` и `/usr/local/bin/node22` в примере являются шаблонами.
В `.htaccess` нельзя подставлять `$HOME` или `~` как в терминале.

`PassengerStartupFile` задается относительно `PassengerAppRoot`, поэтому здесь нужен
именно `server.js`. Директивы описаны в
[документации Passenger для Apache](https://www.phusionpassenger.com/docs/references/config_reference/apache/)
и [примере Спринтхост](https://help.sprinthost.ru/framework/express).

Если в `public_html` остались `index.html`, `index.htm` или `index.php` от предыдущего
сайта, перенесите их в резервный каталог вне `public_html` через файловый менеджер.
Иначе вместо приложения может открываться прежняя главная страница.

Файлы `server.js`, серверный `node_modules` и полный каталог `.next` размещаются только
в каталоге приложения. В `public_html/_next` на этом шаге копируется только `static`.

## 8 Запуск сайта

В панели «Сайты» → «Веб-серверы» выберите **Node.js 22** для `svitya.com` и сохраните
настройку. Если на том же аккаунте есть другие сайты, проверьте, к каким доменам панель
применяет изменение.

После этого на сервере выполните:

```bash
mkdir -p "$SVITYA_RELEASE_DIR/tmp"
touch "$SVITYA_RELEASE_DIR/tmp/restart.txt"
```

Откройте `svitya.com` в браузере. Passenger запускает приложение при обращении к сайту
и управляет его процессом; SSH-соединение можно закрыть после проверки.
Перезапуск через `tmp/restart.txt` описан в
[инструкции Спринтхост](https://help.sprinthost.ru/howto/nodejs).

Для штатной работы здесь достаточно Passenger. Команда `npm run dev` предназначена
для разработки; локальный `npm start` из шага 2 нужен для проверки сборки на Mac.
Открывать порт `3000` посетителям не требуется: адресом сайта управляет веб-сервер хостинга.
Механизм описан в
[документации Passenger о подключении Node.js](https://www.phusionpassenger.com/docs/advanced_guides/in_depth/node/reverse_port_binding.html).

## 9 Домен и HTTPS

Если `svitya.com` уже направлен на этот аккаунт хостинга, используйте существующие
DNS-настройки. При переносе с другого сервера укажите адреса, которые показывает панель
Спринтхост, и проверьте также существующую запись `AAAA`: она не должна вести на старый
сервер. Настройки почты при этом меняются только при переносе самой почты.

В панели «Сайты» → «Мои сайты» включите SSL для `svitya.com`. Дождитесь выпуска
сертификата и проверьте открытие `https://svitya.com/ru/about`. В панели доступен
бесплатный Let's Encrypt с автоматическим продлением; условия для доменов со сторонними
NS и алиасов приведены в
[инструкции по сертификатам](https://help.sprinthost.ru/control-panel/certificates).

После того как HTTPS заработал, добавьте **в начало** `.htaccess`:

```apache
RewriteEngine on
RewriteCond %{HTTP:X-Forwarded-Proto} !https
RewriteRule ^ https://%{HTTP_HOST}%{REQUEST_URI} [L,R=301,NE]
```

Это правило Спринтхост учитывает HTTPS перед фронтендом nginx. См.
[раздел о перенаправлении на HTTPS](https://help.sprinthost.ru/howto/htaccess).
Если перенаправление уже настроено отдельной услугой или внешним прокси, используйте
один согласованный способ, чтобы исключить цикл перенаправлений.

Основной адрес в коде проекта уже установлен как `https://svitya.com` в `app/site.ts`.
Для публикации на этом домене изменять его не нужно. Временный домен подходит для
проверки, но ссылки sitemap и SEO-адреса будут указывать на `svitya.com`.

## 10 Проверка после публикации

На Mac выполните:

```bash
curl -I https://svitya.com/ru/about
curl -I https://svitya.com/en/about
curl -I http://svitya.com/ru/about
curl -I https://svitya.com/sitemap.xml
curl -I https://svitya.com/robots.txt
curl -I https://svitya.com/ru/does-not-exist
curl -I https://svitya.com/cv/en/CV_Strokov_Victor.pdf
```

Ожидаемые результаты:

| Адрес                         | Результат                       |
| ----------------------------- | ------------------------------- |
| `/ru/about`, `/en/about`      | `200`                           |
| HTTP-версия страницы          | Перенаправление на HTTPS, `301` |
| `/sitemap.xml`, `/robots.txt` | `200`                           |
| Несуществующая страница       | `404`                           |
| Файл резюме                   | `200` и тип PDF                 |

Затем проверьте сайт в браузере на компьютере и телефоне:

- обе языковые версии и переход с `/` на выбранный язык;
- прямой переход и обновление страницы `/ru/projects/mappngo`;
- страницы работы, проектов и активностей;
- фотографии и логотипы, включая обработанные изображения `/_next/image`;
- галереи, PDF и скачивание резюме;
- светлую и темную тему, настройки и окно cookie;
- мобильное меню и страницу ошибки 404.

В инструментах разработчика откройте вкладку «Сеть». Запросы к `/_next/static/...`
должны завершаться успешно, а запрос к `/_next/image?...` должен возвращать изображение.
Проверка этого адреса нужна отдельно: она подтверждает работу Linux-версии `sharp`,
а не только загрузку уже готового файла.

`/robots.txt` и `/sitemap.xml` формируются приложением и не лежат в `public` как обычные
файлы. Если страницы открываются, но эти два адреса возвращают ошибку nginx, попросите
поддержку передавать их запросы Apache/Passenger. Такую же проверку выполните для
`/_next/image`: этот адрес обслуживает приложение.

Если PDF обслуживает nginx напрямую, заданный Next.js заголовок `Content-Disposition`
может не применяться. Проверьте названия при сохранении PDF непосредственно из браузера.
Если важно сохранить названия из `src/content/downloads.json`, попросите поддержку
настроить соответствующие заголовки для этих файлов либо передавать их запросы приложению.

## 11 Обновления и возврат к предыдущей версии

Для обновления повторите шаги 2–7 с **новым** именем публикации. До переключения
`PassengerAppRoot` приложение продолжает использовать предыдущую серверную сборку.
Копирование публичных файлов может обновлять материалы действующего сайта, поэтому
выполняйте заключительные шаги подряд в выбранное время публикации.

После подготовки новой версии:

1. Сохраните текущий `.htaccess` и резервную копию `public_html`.
2. Скопируйте публичные файлы и `.next/static` новой версии, как в шаге 7.
3. В `.htaccess` замените `PassengerAppRoot` на каталог новой версии.
4. Создайте `tmp/restart.txt` в каталоге **новой** версии.
5. Повторите проверки из шага 10.

Сохраняйте предыдущий каталог приложения до успешной проверки новой версии.
Старые файлы из `_next/static` также оставляйте на время обновления: открытые вкладки
посетителей могут еще обращаться к ним. Копирование из шага 7 их не удаляет.

При проблемах верните в `.htaccess` прежний `PassengerAppRoot`, восстановите публичные
файлы из резервной копии и создайте `tmp/restart.txt` в прежнем каталоге приложения.
Для восстановления публичных файлов сначала распакуйте архив в отдельную папку:

```bash
SVITYA_BACKUP_RELEASE='20261007-01'
SVITYA_RESTORE_DIR="$HOME/backups/restore-$SVITYA_BACKUP_RELEASE"
mkdir -p "$SVITYA_RESTORE_DIR"
tar -xzf "$HOME/backups/svitya-public-html-$SVITYA_BACKUP_RELEASE.tar.gz" \
  -C "$SVITYA_RESTORE_DIR"
```

Через файловый менеджер перенесите текущий `public_html` в отдельный резервный каталог
и создайте `public_html` с содержимым распакованной копии, включая `.htaccess`.
Так файлы новой версии не смешаются с восстановленной версией. При возврате к сайту,
который ранее работал на PHP или Apache без Node.js, верните также прежний веб-сервер
в панели. На время такого восстановления возможен короткий перерыв.

После успешной публикации можно удалить входящий архив `~/svitya-linux-ИМЯ_ПУБЛИКАЦИИ.tar.gz`
на сервере и временный каталог `deploy/linux-build-ИМЯ_ПУБЛИКАЦИИ` на Mac.
Рабочий каталог `~/apps/svitya/releases/...` и последнюю исправную версию сохраняйте.

## 12 Альтернатива после обновления Node.js: сборка на сервере

Этот вариант заменяет шаг 6, если поддержка обновила `node22` до **22.12.0 или новее**
и на тарифе достаточно ресурсов для сборки. На подтвержденной версии `v22.9.0`
его не выполняйте: используйте основной вариант через Docker.

После создания архива по шагу 5 отправьте **исходники с Mac**:

```bash
SVITYA_RELEASE='20261007-01'
SVITYA_LOGIN='LOGIN'
SVITYA_SERVER='SERVER_IP'
scp "/tmp/svitya-source-$SVITYA_RELEASE.tar.gz" \
  "$SVITYA_LOGIN@$SVITYA_SERVER:~/"
```

Вернитесь в **SSH-сессию**. Сначала проверьте обновленную версию:

```bash
node22 --version
npm22 --version
```

Если `node22` по-прежнему показывает `v22.9.0`, остановитесь.
В противном случае подготовьте новые пустые каталоги:

```bash
SVITYA_RELEASE='20261007-01'
SVITYA_SOURCE="$HOME/builds/svitya/$SVITYA_RELEASE"
SVITYA_RELEASE_DIR="$HOME/apps/svitya/releases/$SVITYA_RELEASE"
mkdir -p "$SVITYA_SOURCE" "$SVITYA_RELEASE_DIR"
tar -xzf "$HOME/svitya-source-$SVITYA_RELEASE.tar.gz" -C "$SVITYA_SOURCE"
```

Настройте Node.js 22 для команд внутри `npm`-скриптов. Изменение `PATH` действует
только в текущей SSH-сессии:

```bash
SVITYA_NODE22="$(command -v node22)"
mkdir -p "$HOME/.local/svitya-node22/bin"
ln -sf "$SVITYA_NODE22" "$HOME/.local/svitya-node22/bin/node"
export PATH="$HOME/.local/svitya-node22/bin:$PATH"
node --version
```

Последняя команда должна показать Node.js 22.12.0 или новее в ветке 22.
При ошибке или более старой версии не продолжайте. Соберите сайт:

```bash
cd "$SVITYA_SOURCE"
npm22 ci --include=dev
npm22 run build
```

Только после успешного завершения скопируйте комплект и проверьте зависимости:

```bash
cp -a "$SVITYA_SOURCE/.next/standalone/." "$SVITYA_RELEASE_DIR/"
mkdir -p "$SVITYA_RELEASE_DIR/tmp"
cd "$SVITYA_RELEASE_DIR"
node22 --check server.js
node22 -e 'console.log(require("sharp").versions)'
```

После проверки продолжайте с шага 7. Если сборка завершается с `Killed` или ошибкой
нехватки памяти, используйте шаг 6 и новое имя публикации. Готовое приложение требует
меньше ресурсов, чем его сборка, поэтому такая ошибка сама по себе не определяет
возможность запуска сайта на тарифе.

## 13 Если сайт не открывается

| Симптом                                       | Что проверить                                                                          |
| --------------------------------------------- | -------------------------------------------------------------------------------------- |
| `node22: command not found`                   | Доступность Node.js 22 на вашем аккаунте                                               |
| `Cannot connect to the Docker daemon`         | Запущен ли Docker Desktop на Mac                                                       |
| `EBADENGINE`, ошибка Vitest при сборке        | Версию Node.js в среде сборки; на `22.9.0` сайт не собираем                            |
| `Killed`, нехватка памяти во время сборки     | Память Docker Desktop; при сборке на хостинге используйте шаг 6                        |
| Старая главная или заглушка хостинга          | Старые `index.html`, `index.htm`, `index.php` в `public_html`                          |
| `500` сразу после изменения `.htaccess`       | Директивы, полный путь к приложению и интерпретатору; ошибки Apache                    |
| Ошибка запуска Passenger                      | Node.js 22 для домена, `PassengerAppRoot`, наличие `server.js` и `.next`               |
| Страница без стилей                           | Наличие `public_html/_next/static` и успешную загрузку его файлов                      |
| `500` на изображениях                         | Linux-зависимости `sharp`, результат `require("sharp")`, права на каталог кеша `.next` |
| Ошибка PDF или резюме                         | Соответствующий файл из `public` скопирован в `public_html`                            |
| nginx возвращает `404` для sitemap или robots | Передачу запросов `/sitemap.xml` и `/robots.txt` приложению                            |
| Цикл перенаправлений                          | HTTPS и наличие нескольких правил перенаправления                                      |
| После обновления старая серверная версия      | Новый `PassengerAppRoot` и `tmp/restart.txt` в новом каталоге                          |

При ошибке запуска сначала посмотрите журнал Apache/Passenger для домена. Если журнал
не доступен в панели или по SSH, попросите поддержку прислать ошибку запуска приложения
и укажите домен, время обращения, путь `PassengerAppRoot` и требуемую версию Node.js 22.
Серверная часть должна иметь доступ на чтение к файлам сборки и на запись к своему
каталогу кеша; файлы принадлежат вашему аккаунту.

Конкретный запуск Next.js через Passenger нужно подтвердить на вашем аккаунте проверками
из шага 10: сочетание версии Passenger, настроек nginx и ограничений тарифа определяет
результат. До завершения этой проверки сохраняйте резервную копию действующего сайта.
